# Requirements

This document turns the project vision into testable requirements. IDs are stable and are referenced
from the component docs. Priority:

- **Must**: required for v1.
- **Should**: v1 if it falls out of the Must work cheaply; otherwise first follow-up.
- **Later**: designed for now (the format and APIs must not block it), built after v1. See [roadmap](roadmap.md).

## Users and core scenario

The primary user is a developer facing a Python project they did not write (written by a colleague or
generated by an AI agent). Core scenario, also the v1 success criterion:

> Run one test or script of an unknown Python project under VizControl, open the viewer, and, mainly by
> using the graph, identify: the entry point, the call path across files and functions, the data passed
> between instrumented calls, the captured value transformations, and the final result. If it failed, also
> identify where and in what context. No LLM explanation, no manual walk through every file.

## Functional requirements

### Starting a run

| ID | Requirement | Priority |
|---|---|---|
| FR-RUN-1 | Trace a Python script: `vizcontrol run path/to/script.py [args...]`. | Must |
| FR-RUN-2 | Trace a module: `vizcontrol run -m package.module [args...]`. | Must |
| FR-RUN-3 | Trace a block or a function from Python code (context manager and decorator). | Must |
| FR-RUN-4 | Trace a single pytest test, one run per test, with the assertion outcome recorded (`pytest --vizcontrol`). | Should (done) |
| FR-RUN-5 | Trace an HTTP request handled by an ASGI app (FastAPI), one run per request. | Later |
| FR-RUN-6 | The traced program keeps its normal behaviour: same stdout/stderr, exit code, `sys.argv`, `__main__`. | Must |

### Capture

| ID | Requirement | Priority |
|---|---|---|
| FR-CAP-1 | Record every call start, return, raise and unwind of Python functions in the included code, with its code location (file, qualified name, line). | Must |
| FR-CAP-2 | Record the caller of each call, so that the call tree can be rebuilt exactly. | Must |
| FR-CAP-3 | Record wall-clock start and end time of each call (monotonic, nanoseconds). | Must |
| FR-CAP-4 | Record call arguments and return values as bounded values. | Must |
| FR-CAP-5 | Record locals snapshots at configurable points: at return, at raise, optionally at every line of selected functions. | Must (return/raise), Should (per line) |
| FR-CAP-6 | Record exceptions: type, message, traceback locations, and the call where they were raised and where they were caught or escaped. | Must |
| FR-CAP-7 | Filter what is instrumented: include/exclude by module glob and path. Defaults: the user's project code only; stdlib and site-packages excluded. | Must |
| FR-CAP-8 | Calls into excluded or native code that are made from included code are recorded as opaque leaf calls ("not observed inside"). | Must |
| FR-CAP-9 | Capture levels: `calls` (structure only), `values` (plus args/return/exception), `state` (plus locals snapshots). | Must |
| FR-CAP-10 | Hard limits: max calls per run, max depth, max value size, max snapshots. When a limit is hit, capture degrades (e.g. drops values) and the run records that it was truncated and where. | Must |
| FR-CAP-11 | Record calls from every thread, tagged with their thread id. | Should |
| FR-CAP-12 | Capture coroutine/async task boundaries so async call trees are meaningful. | Later |

### Values and objects

| ID | Requirement | Priority |
|---|---|---|
| FR-VAL-1 | Serialization never calls user code with side effects. No `__repr__` by default for user classes; reads attributes from `__dict__`/`__slots__` instead. | Must |
| FR-VAL-2 | Values are bounded in depth, collection length, string length and total bytes. Truncation is explicit in the stored value. | Must |
| FR-VAL-3 | Each mutable object gets a per-run object id, so the same object can be followed across calls and snapshots. | Must |
| FR-VAL-4 | Sensitive data is redacted before it is written: default key patterns (`password`, `token`, `secret`, `authorization`, `api_key`, ...) plus user rules. | Must |
| FR-VAL-5 | Users can register custom serializers for their own types. | Should |

### Trace model and persistence

| ID | Requirement | Priority |
|---|---|---|
| FR-PER-1 | Every run is saved to a single self-contained `.vizc` file (SQLite) that can be reopened later without the original process. | Must |
| FR-PER-2 | A run file stores metadata: command, argv, cwd, Python version, start/end time, outcome, VizControl version, capture config, truncation info. | Must |
| FR-PER-3 | A run file stores the source of the executed files (or a hash plus path when disabled), so code can be shown even if the project changed. | Should |
| FR-PER-4 | A run whose process crashed or was killed keeps everything flushed so far and is marked `unfinished`. | Must |
| FR-PER-5 | The file format is versioned; the reader rejects unknown major versions with a clear message. | Must |

### Analysis

| ID | Requirement | Priority |
|---|---|---|
| FR-ANA-1 | Rebuild the hierarchical call tree from events. | Must |
| FR-ANA-2 | Group calls into Level‑1 stages (default: by top-level package/module path, overridable by user rules). | Must |
| FR-ANA-3 | Aggregate repeated calls (same code location, same parent) into one collapsible group with a count. | Must |
| FR-ANA-4 | Derive data-flow links: an object id that leaves a call (return, mutated argument) and enters another (argument) creates a link. | Should |
| FR-ANA-5 | Extract the error path: from the root to the call where the exception originated, plus the propagation path. | Must |
| FR-ANA-6 | Compute value changes for an object id across snapshots (field-level diff). | Should |
| FR-ANA-7 | Compare two runs and report the first divergence point and the differing subtrees. | Later |
| FR-ANA-8 | Search calls by function/module name and values by variable name or content. | Should |

### Visualization (viewer)

| ID | Requirement | Priority |
|---|---|---|
| FR-VIZ-1 | **Level 1, overview**: show the run as a pipeline of stages with the main path highlighted. | Must |
| FR-VIZ-2 | **Level 2, components**: expanding a stage shows its modules, classes and functions and the call edges between them. | Must |
| FR-VIZ-3 | **Level 3, function**: selecting a call shows location, caller, args, return, duration, exception, children, snapshots. | Must |
| FR-VIZ-4 | **Level 4, values**: expand complex objects; see a value's evolution over the run and compare two states. | Must (expand), Should (evolution/compare) |
| FR-VIZ-5 | Navigation keeps context: breadcrumb of the current path, back/forward, zoom to node, no full-page reloads. | Must |
| FR-VIZ-6 | Collapse, expand, filter (by module, outcome, duration) and hide subtrees. | Must |
| FR-VIZ-7 | Node states are visually distinct: `ok`, `raised`, `unfinished`, `not observed` (opaque), `truncated`. | Must |
| FR-VIZ-8 | On a failed run, open on the failure: error path highlighted, failing call selected. | Must |
| FR-VIZ-9 | Show the source code around a call's location, highlighting the line of the call/raise. | Should |
| FR-VIZ-10 | **Data Flow view**: object lifecycles across calls, linked to the Execution Flow view both ways. | Should |
| FR-VIZ-11 | **Diff view**: two runs side by side with the divergence point marked. | Later |
| FR-VIZ-12 | Chronological replay of events (timeline scrubber). | Later |
| FR-VIZ-13 | Every displayed fact shows its provenance when not directly observed (inferred link, not captured). | Must |

## Non-functional requirements

| ID | Requirement |
|---|---|
| NFR-PERF-1 | Excluded code and C calls run at near-native speed (instrumentation disabled per code object and per call site, not filtered per event): ≤ 1.2× on the app-like workload of `benchmarks/overhead.py` at any level. Each traced call costs ≤ 5 µs at `calls` level on the reference machine, so the worst case (thousands of tiny traced functions) is bounded by per-call cost, not by a ratio. |
| NFR-PERF-2 | Memory in the traced process is bounded: events are buffered and flushed in batches; buffer size is configurable. |
| NFR-PERF-3 | The viewer stays responsive on a run with 1,000,000 calls: the server returns slices, the viewer never loads the whole tree. |
| NFR-SAFE-1 | Capture must never change program semantics: no exceptions leak from the tracer, no user `__repr__`/properties/descriptors evaluated by default, no reference kept that prevents objects from being freed after the run. |
| NFR-SAFE-2 | Redaction happens in the traced process before data reaches disk. |
| NFR-SAFE-3 | The server binds to `127.0.0.1` by default and serves only the given trace files. |
| NFR-OBS | Observability limits are explicit. Each fact is one of **observed** (recorded event), **not captured** (excluded, native, truncated, redacted) or **inferred** (derived by analysis, e.g. stage grouping, data-flow links). The format stores which is which, and the UI shows it. |
| NFR-DEC-1 | Capture and visualization are independent: capture depends only on the stdlib, and the viewer only on the trace format and server API. |
| NFR-AI-1 | No LLM or network service is required for any feature. Optional AI features, if any, read only the stored trace. |
| NFR-PKG-1 | One package, `pip install vizcontrol`, Python ≥ 3.12, zero mandatory runtime dependencies. The viewer ships prebuilt inside the wheel. |
| NFR-PKG-2 | Works offline. No telemetry. |

## Out of scope for v1

- Distributed tracing across processes/services; subprocesses are not followed.
- Languages other than Python.
- Line-by-line stepping of whole programs (per-line capture is opt-in per function).
- Editing or re-running code from the viewer.
- Multi-user sharing or hosting; export is "send the `.vizc` file".
